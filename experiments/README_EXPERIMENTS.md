## Эксперимент 1. Измеренный FPR и теоретическая оценка

### Цель

Сравнить фактическую частоту ложноположительных срабатываний фильтра Блума с теоретическим значением при целевой вероятности 1%.

### Методика

1. Построить фильтр по всему уникальному набору RockYou с целевым FPR 0,01.
2. Проверить 100 000 строк, которые отсутствуют в исходном наборе.
3. Проверить выборку из 10 000 существующих паролей на ложные отрицания.
4. Сравнить измеренный FPR с теоретической оценкой.

Теоретическая оценка:

\[
p_{theory} = \left(1-e^{-kn/m}\right)^k,
\]

где \(n\) — количество вставленных элементов, \(m\) — количество битов фильтра, \(k\) — число хеш-функций.

Измеренная оценка:

\[
p_{measured} = \frac{FP}{N_{probes}},
\]

где \(FP\) — число ложноположительных срабатываний, а \(N_{probes}\) — число проверенных отсутствующих строк.

### Команда запуска

```bash
python3 experiments/experiment_fpr.py rockyou_full.txt rockyou_1pct.bloom
```

## Эксперимент 2. Влияние количества вставленных элементов на FPR

### Цель

Исследовать, как меняются заполненность битового массива и вероятность ложноположительного срабатывания при увеличении числа вставленных элементов.

### Идея и контролируемые параметры

Размер битового массива \(m\) и число хеш-функций \(k\) фиксируются по фильтру, построенному для полного датасета. Создаётся новый пустой фильтр с теми же \(m\) и \(k\), после чего элементы добавляются порциями до контрольных точек 1%, 5%, 10%, 25%, 50%, 75% и 100% от размера уникального датасета. На каждой точке используется один и тот же набор отсутствующих тестовых строк.

Теоретическая кривая рассчитывается по формуле:

\[
p(n) = \left(1-e^{-kn/m}\right)^k.
\]

В этой серии меняется только число вставленных элементов \(n\). Поскольку \(m\) и \(k\) остаются постоянными, с ростом \(n\) ожидается увеличение заполненности битов и FPR.

### Команда запуска

Убедитесь, что `rockyou_1pct.bloom` был построен на том же полном файле `rockyou_full.txt`, который передаётся первым аргументом:

```bash
python3 experiments/experiment_growth.py rockyou_full.txt rockyou_1pct.bloom
```

По умолчанию скрипт выполняет 100 000 проверок отсутствующих строк на каждой контрольной точке. Для быстрого предварительного прогона можно уменьшить число запросов:

```bash
python3 experiments/experiment_growth.py rockyou_full.txt rockyou_1pct.bloom --probes 10000
```

Результаты сохраняются в `results/fpr_growth.csv`. После выполнения сохраните CSV, пришлите его содержимое и добавьте итоговые числа в раздел «Результаты эксперимента 2» ниже.

### Важные замечания

- Скрипт загружает уникальные пароли в `set`, поэтому потребление памяти может составлять значительную часть памяти компьютера, как и при построении исходного фильтра.
- Порядок обхода `set` в Python не гарантирован между отдельными запусками. Набор тестовых проб воспроизводим по `--seed`, но точные значения на промежуточных контрольных точках могут немного отличаться между запусками.
- Контрольная точка 100% должна иметь те же `m` и `k`, что и сохранённый фильтр, и добавлять столько же элементов. Биты могут отличаться из-за порядка вставки, но число элементов и теоретический FPR должны совпадать.
- Не интерпретируйте время построения как только время хеширования: оно включает накладные расходы Python и текущей реализации.

## Эксперимент 3. Влияние количества хеш-функций k

### Цель

Измерить, как количество хеш-функций влияет на заполненность фильтра, фактический и теоретический FPR, а также время вставки и проверки.

### Методика

- Используется весь набор уникальных паролей RockYou.
- Размер битового массива `m` фиксируется по фильтру `rockyou_1pct.bloom`.
- Число хеш-функций `k` меняется; по умолчанию используются значения 3, 5, 7, 9 и 11.
- Для каждого значения создаётся отдельный пустой фильтр, в который добавляются все пароли.
- На каждом фильтре проверяется один и тот же набор из 100 000 строк, отсутствующих в датасете.
- Сохраняются FPR, заполненность, время вставки и среднее время проверки.

Формула теоретического FPR остаётся:

\[
p = \left(1-e^{-kn/m}\right)^k.
\]

При фиксированных `m` и `n` теоретический оптимум для `k` приблизительно равен `(m/n) ln 2`. Для использованных параметров `m = 137 491 816` и `n = 14 344 390` оптимум составляет примерно 6,64, то есть `k = 7` является ближайшим целым значением.

### Команда запуска

```bash
python3 experiments/experiment_k.py rockyou_full.txt rockyou_1pct.bloom
```

По умолчанию выполняется пять полных построений фильтра. Это может занять несколько минут. Для предварительного прогона можно сократить число тестовых запросов, но вставка полного набора всё равно будет выполнена для каждого `k`:

```bash
python3 experiments/experiment_k.py rockyou_full.txt rockyou_1pct.bloom --probes 10000
```

Чтобы изменить набор значений `k`:

```bash
python3 experiments/experiment_k.py rockyou_full.txt rockyou_1pct.bloom --k-values 5,6,7,8,9
```

CSV сохраняется в `results/fpr_by_k.csv`. Сравнивайте не только FPR, но и время: увеличение `k` означает больше операций на каждый запрос.

### Интерпретация

Минимальный измеренный FPR среди испытанных вариантов получен при `k = 7`: 980 ложноположительных срабатываний из 100 000 запросов, или 0,98%. Это согласуется с оценкой оптимального числа хеш-функций:

\[
k_{opt} = \frac{m}{n}\ln 2 = \frac{137\,491\,816}{14\,344\,390}\ln 2 \approx 6{,}64.
\]

Следовательно, ближайшее целое значение — `k = 7`. При слишком малом `k` больше битов остаётся свободными, но вероятность случайного совпадения выше; при слишком большом `k` занято больше битов и каждый запрос требует дополнительных вычислений. В измерениях среднее время проверки выросло с 1,874 мкс при `k = 3` до 2,830 мкс при `k = 11`.

Теоретическая и измеренная оценки близки, но не обязаны совпадать точно: фактическая оценка зависит от конечной выборки из 100 000 запросов. Измеренный минимум на `k = 7` также не доказывает, что он будет минимальным для любой возможной выборки, но теория независимо предсказывает это значение как оптимальное для выбранных `m` и `n`.

## План следующих экспериментов

4. **Сравнение с `set`:** сравнить скорость проверки и потребление памяти с учётом того, что `set` хранит сами строки, а Bloom filter — битовый массив.

### Эксперимент 4. Сравнение Bloom filter с Python `set`

**Цель:** сравнить время проверки существования элемента и приблизительное потребление памяти двумя структурами на одном наборе паролей.

Скрипт `experiments/experiment_set.py` загружает уникальные пароли, проверяет, что сохранённый Bloom filter построен для того же числа элементов, а затем измеряет lookup для Bloom filter и `set` на одинаковых отсутствующих пробах и на одинаковой выборке существующих паролей. Оценка памяти для `set` включает размер таблицы и размеры строковых объектов; это оценка используемой Python-структурами памяти, но не полный RSS процесса. Размер Bloom filter берётся из сохранённого файла.

Запуск:

```bash
python3 experiments/experiment_set.py rockyou_full.txt rockyou_1pct.bloom
```

Для предварительного прогона:

```bash
python3 experiments/experiment_set.py rockyou_full.txt rockyou_1pct.bloom --probes 10000 --positive-probes 1000
```

Результаты сохраняются в `results/set_comparison.csv`. Скрипт не заменяет и не изменяет существующий `bloom_filter.py`. Перед запуском убедитесь, что на компьютере достаточно оперативной памяти: Python `set` с более чем 14 миллионами строк может занимать существенно больше памяти, чем сам Bloom filter.

Оценка памяти для `set` включает таблицу хешей и строковые объекты Python; это оценка памяти структур, а не полный RSS процесса.

### Интерпретация

В этом измерении Bloom filter занял примерно в 79,5 раза меньше памяти, чем `set`. В свою очередь, `set` проверял элементы примерно в 19,8 раза быстрее для отсутствующих строк и в 20,0 раза быстрее для существующих. Это результат конкретной реализации и конкретного компьютера; время зависит от оборудования, версии Python, нагрузки и способа измерения.

Bloom filter допускает ложноположительные ответы, но при корректной реализации не должен давать ложноотрицательные ответы для элементов, которые были добавлены и не удалялись. В эксперименте получено 1 072 ложноположительных ответа из 100 000 проверок (1,072%); теоретическая оценка исходной конфигурации составляет около 1,004%. Разница ожидаема при конечной тестовой выборке. `set` точно проверяет принадлежность строки.

Вывод: Bloom filter подходит, когда критична экономия памяти и допустима последующая точная проверка положительных ответов. Если память доступна и требуется точное и быстрое членство, обычный `set` в этом эксперименте оказался быстрее.

## Эксперимент 5. Сравнение с индексированной SQLite

### Цель и методика

Сравнить проверку принадлежности в Bloom filter с запросом к SQLite-таблице, где пароль является первичным ключом (`TEXT PRIMARY KEY`, `WITHOUT ROWID`). Скрипт отдельно измеряет создание базы, время проверок отсутствующих и существующих строк, количество ложноположительных ответов и размер файла SQLite.

**Важное ограничение:** Bloom filter находится в оперативной памяти, а SQLite хранит индекс и строки в файле на диске. Поэтому размер SQLite-файла нельзя напрямую трактовать как потребление RAM; результаты сравнивают разные варианты хранения и доступа, а не идентичные условия памяти. Время SQLite также включает накладные расходы Python и SQL-запроса.

### Команды запуска

```bash
python3 experiments/experiment_sqlite.py rockyou_full.txt rockyou_1pct.bloom
```

Для короткого измерения запросов (база всё равно строится по полному датасету):

```bash
python3 experiments/experiment_sqlite.py rockyou_full.txt rockyou_1pct.bloom --probes 10000 --positive-probes 1000
```

### Интерпретация

В этом запуске файл SQLite занимал примерно в 20,2 раза больше места, чем битовый массив Bloom filter. Проверка отсутствующей строки в Bloom filter была примерно в 1,95 раза быстрее, чем запрос к SQLite; для существующей строки — примерно в 2,69 раза быстрее. При этом сравнение не полностью эквивалентно по условиям хранения: битовый массив Bloom filter находится в RAM, а размер SQLite измерен по файлу на диске. Реальное время SQLite зависит в том числе от кэширования страниц ОС и состояния диска.

Bloom filter вернул положительный результат для 997 из 100 000 отсутствующих строк (0,997%). Это близко к теоретическому FPR исходной конфигурации — около 1,004%. SQLite не дал ложноположительных или ложноотрицательных ответов в измеренных выборках. Ноль ложных срабатываний в выборке не является универсальным доказательством корректности всех возможных запросов, но для точного индексированного поиска ожидается точное совпадение строк.

**Уточнение по времени построения:** значение 17,13 секунды в CSV — время создания SQLite-базы и индекса. Скрипт записывает это одно значение в обе строки CSV, поэтому оно не является временем построения Bloom filter. Время первоначального построения фильтра из эксперимента 1 было около 57,9 секунды; напрямую сравнивать эти значения следует осторожно, так как замер и этапы работы различаются.

### Общий вывод по трём структурам

- **Bloom filter** — минимальное потребление памяти/хранилища в этих измерениях и вероятностный результат: возможны ложноположительные ответы.
- **Python `set`** — самый быстрый lookup в проведённом эксперименте, но очень высокая оценка потребления RAM.
- **SQLite с индексом** — точный поиск с сохранением данных на диске, но более крупный файл и более медленные запросы в данном сценарии.

Эти результаты относятся к конкретной реализации, параметрам, компьютеру и способу измерения; их не следует считать универсальным рейтингом структур данных.

Каждый эксперимент следует запускать и проверять отдельно, прежде чем переходить к следующему.
